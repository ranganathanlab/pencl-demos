Generalization-Preserving Fine-tuning of BioM3 · Didactic Note 18

PenCL on Aurora: porting contrastive pretraining to Intel XPU

PenCL retraining requires the full 49.8 million pair corpus to pass through both ESM2 (650M parameters) and PubMedBERT (100M parameters) for 10 epochs, with contrastive and masked-language losses computed on every batch. This is a multi-day distributed training job. Aurora — the ALCF exascale system with 10,624 nodes of Intel Ponte Vecchio GPUs — provides the scale. This note documents the port from NVIDIA CUDA to Intel XPU: the failures, the fixes, and the path from one GPU tile to multi-node production.

Ranganathan Lab · Center for Physics of Evolving Systems · University of Chicago BioM3 ProteoScribe · Aurora Deployment · April 2026

Section 1 · Why Aurora

The training job exceeds what any single GPU can deliver

PenCL training iterates through 5.05 million SwissProt rows per epoch, each paired with a randomly sampled Pfam protein from the same family. At each step, the model processes both proteins through ESM2 (33 transformer layers, 650M parameters) and both text descriptions through PubMedBERT (12 transformer layers, 100M parameters), projects both into a shared 256-dimensional space, and computes four losses: global contrastive alignment (ℒGC), protein family contrastive (ℒPFC), and two masked-language objectives (ℒbML, ℒpML).

On a single NVIDIA A100, one epoch takes roughly 18 hours. Ten epochs — the minimum for the embedding geometry to reshape — would take a week. This is acceptable for a one-off training run, but we are running a controlled experiment: Run 1 (corpus diversity alone) and Run 2 (corpus + sector annotations + ℒsector), plus potential hyperparameter sweeps. The experiment needs parallelism.

Polaris (ALCF)

4× NVIDIA A100 per node. CUDA + NCCL. Known to work — the original PenCL was trained here. 4-GPU DDP gives ~4× speedup. 10 epochs ≈ 2 days.

Aurora (ALCF)

6× Intel Ponte Vecchio per node, 2 tiles each = 12 compute units. XPU + oneCCL. At 4 nodes (48 tiles), each tile at 80% of A100 speed, effective throughput ≈ 38× A100. 10 epochs ≈ 12 hours.

Aurora's advantage is not per-tile performance — each tile runs at roughly 80% of an A100. The advantage is density: 12 tiles per node versus 4 GPUs. At equal node count, Aurora provides 3× more parallelism. At 4 nodes, the effective throughput makes 10-epoch experiments feasible in half a day instead of two days.

Section 2 · The port

CUDA to XPU is not a search-and-replace

BioM3's codebase was written for NVIDIA GPUs. Porting to Aurora's Intel XPU requires changes at three levels: device placement (where tensors live), numerical operations (what happens to them), and distributed communication (how GPUs talk to each other). The first two were solved during the March 2026 inference port. The third — distributed training — is the subject of this note.

Section 3 · Training-specific problems

Inference worked; training required five additional fixes

Inference is a forward pass. Training adds the backward pass, the optimizer step, the contrastive loss computation with its infinity-masked diagonal, and — critically — the distributed communication calls that synchronize gradients across GPUs. Each of these introduced failures on XPU that did not appear during inference.

Fix 1: Distributed guards on barrier and all_gather

The PenCL training code was written for multi-GPU NVIDIA DDP. Every training step calls dist.barrier() (wait for all GPUs to synchronize) and self.all_gather() (collect embeddings from all GPUs for the contrastive loss) — 13 barrier calls and 12 all_gather calls across the three PL wrapper classes. On a single XPU tile without a DDP process group, every one of these hangs or crashes.

def _safe_barrier(): if dist.is_initialized(): dist.barrier() def _safe_all_gather(module, tensor, sync_grads=True): if dist.is_initialized(): return module.all_gather(tensor, sync_grads=sync_grads) return tensor

Global replacement: every dist.barrier() becomes _safe_barrier(), every self.all_gather() becomes _safe_all_gather(self, ...). In single-tile mode, the guards short-circuit. In multi-tile mode with DDP initialized, they pass through to the real distributed calls.

Fix 2: bf16 infinity masking

The contrastive loss masks the diagonal of the logits matrix with negative infinity — excluding self-comparisons so the model learns to match text to the correct protein, not itself. On CUDA with fp32, float('-inf') is representable. On XPU, the tensor can silently auto-cast to bf16, where infinity is not representable — causing a crash in set_inf() inside compute_inter_loss().

The fix: cast to fp32 before applying the infinity mask, or set precision to '32' globally to avoid bf16 entirely. We chose the latter for the initial port — correctness first, performance later.

Fix 3: Missing import

The memory logging function print_memory_usage() in helper_funcs.py called os.getpid() without importing os. This was masked on CUDA because pynvml was imported first (which imports os as a side effect). On XPU, with pynvml wrapped in a try/except, the import was missing. The training loop completed the forward pass, backward pass, and loss computation — then crashed on the logging call at the end of the step.

Lost outputs. Two debug jobs ran with the bf16 and barrier fixes but before the import os fix. Both crashed at the same point (the logging call after the first training step) but wrote their logs to the same path, overwriting each other. We diagnosed the issue only after switching to unique log filenames with -j oe (join stdout/stderr) in the PBS script. Lesson: always use unique log paths on shared job schedulers.

Fix 4: Autocast disabled

PyTorch Lightning's mixed-precision plugin checks for CUDA to enable torch.autocast. On XPU, the check fails and autocast is silently disabled, leaving the model in full fp32. This is correct but slow. The XPU-native autocast (torch.autocast(device_type="xpu", dtype=torch.bfloat16)) exists in PyTorch 2.10 but must be invoked manually — PL's plugin doesn't know about it. For the initial port, we set precision='32' to remove the ambiguity entirely.

Fix 5: Trainer configuration

The working Trainer configuration for single-tile XPU:

accelerator = 'auto' # custom PL from ALCF auto-detects XPU strategy = 'auto' # no DDP for single tile precision = '32' # fp32 everywhere, no autocast ambiguity devices = 1 # one tile

The 13 minutes per step is dominated by JIT kernel compilation on the first few batches — Intel's compiler generating optimized XPU kernels for every operation in ESM2 and PubMedBERT. After warmup, subsequent steps will be significantly faster. But single-tile fp32 is fundamentally too slow for production: 6,577 steps per epoch × 13 minutes = 57 days per epoch. The code is clean. Every component of the PenCL training loop works on Intel XPU: ESM2 forward and backward, PubMedBERT forward and backward, contrastive loss with infinity masking, intra-modal loss, masked-language losses, optimizer step, PL logging, and checkpointing. The remaining work is purely about distributed communication — scaling from one tile to many.

Section 5 · The scaling path

From one tile to 48: three phases of distributed training

Aurora nodes contain 6 Intel Ponte Vecchio GPUs, each with 2 compute tiles — 12 tiles per node, each with ~64 GB of HBM. For distributed data-parallel (DDP) training, each tile is one rank: it holds a complete copy of the model, processes a different batch of data, and exchanges gradients with all other ranks after each step.

PyTorch 2.8 introduced native support for Intel GPU distributed training via the XCCL backend — a direct integration of Intel's oneCCL communication library into PyTorch's distributed framework. This replaces the older external oneccl_bindings_for_pytorch package. XCCL has been validated at scale on Aurora: up to 2,048 nodes (24,576 ranks) with 89% scaling efficiency for DDP workloads.

Phase 0 — Single tile (confirmed)
1 tile, fp32, no DDP. Validates the training loop. 13 min/step.
Phase 1 — Single node, 12 tiles
mpiexec launches 12 ranks, one per tile. torch.distributed.init_process_group(backend="xccl") before PL. Each rank runs PL with devices=1, strategy='ddp'. Intra-node communication via shared memory.
Phase 2 — Multi-node, 4 × 12 = 48 tiles
Same mpiexec pattern across 4 nodes. MASTER_ADDR from $PBS_NODEFILE. Inter-node communication via Slingshot fabric. Effective batch size: 48 × 8 × 2 = 768.
Phase 3 — Production Run 1
4 nodes, 36-hour walltime, 10 epochs. Checkpoint every epoch. Resume from last.ckpt if interrupted. Embedding geometry evaluation at epochs 2, 5, 10.

The key architectural decision: bypass PL's DDP launcher and use mpiexec directly. Each MPI rank initializes torch.distributed with the XCCL backend using PALS environment variables (PALS_WORLD_SIZE, PALS_RANKID, PALS_LOCAL_RANKID) set automatically by Aurora's job scheduler. PL then sees an already-initialized process group and wraps the model in DDP transparently.

# In PL_training.py, after arg parsing, before model creation: if int(os.environ.get("PALS_WORLD_SIZE", 1)) > 1: world_size = int(os.environ["PALS_WORLD_SIZE"]) rank = int(os.environ["PALS_RANKID"]) local_rank = int(os.environ["PALS_LOCAL_RANKID"]) dist.init_process_group( backend="xccl", # native PyTorch 2.8+ init_method="env://", world_size=world_size, rank=rank ) torch.xpu.set_device(local_rank)

The 2 seconds per step estimate is based on A100 throughput (scaled to 80% for XPU) after JIT warmup. The actual per-step time at 48 tiles will depend on gradient synchronization overhead — the AllReduce for 107M trainable parameters across 48 ranks via the Slingshot network. At 89% scaling efficiency (the benchmark number for XCCL on Aurora), the effective time is ~2.2 seconds per step, giving ~4.0 hours per epoch.

Why 10 epochs? We do not know a priori how many epochs are needed. The original PenCL used 5 epochs for the design application and 20 for benchmarking. Our corpus is 9× larger per protein (9 text variants) but also 9× more diverse. We start with 10, checkpoint every epoch, and evaluate embedding geometry at epochs 2, 5, and 10. If format invariance plateaus before epoch 10, we stop early. If it hasn't converged by epoch 10, we extend.
