Generalization-Preserving Fine-tuning of BioM3 · Didactic Note 18

PenCL on Aurora: porting contrastive pretraining from CUDA to Intel XPU

This note documents the complete port of PenCL — a contrastive learning model that jointly embeds protein sequences and text descriptions — from NVIDIA CUDA to Intel XPU on the ALCF Aurora supercomputer. PenCL retraining requires 49.8 million text-protein pairs to pass through ESM2 (650M parameters) and PubMedBERT (100M parameters) for 10 epochs, with contrastive and masked-language losses computed on every batch. Aurora provides the scale: 10,624 nodes of Intel Ponte Vecchio GPUs. But CUDA code does not run on XPU. This note catalogs every failure we encountered and the fix for each — at the level of detail needed for someone facing the same problems to solve them.

Ranganathan Lab · Center for Physics of Evolving Systems · University of Chicago Addison Howe and Tarak Nandi · BioM3 ProteoScribe · Aurora Deployment · April 2026

Section 1 · The landscape

Aurora hardware, the software stack, and why this port was non-trivial

Aurora is the first exascale system built entirely on Intel GPUs. Each node contains 6 Intel Data Center GPU Max 1550 (Ponte Vecchio) — each with 2 compute tiles, 128 GB HBM2e, and 128 Xe-HPC cores. The two tiles within a GPU share HBM but each is an independent compute unit: it gets its own process, its own device address, its own memory allocation. For distributed training, 1 tile = 1 rank. A single Aurora node has 12 ranks, 768 GB of HBM, ~1 TB of DDR5 system memory, and 8 Slingshot-11 NICs for inter-node communication.

Every layer of the stack changed. The GPU architecture changed from NVIDIA Ampere to Intel Ponte Vecchio. The distributed communication changed from NCCL to XCCL. The Lightning version jumped from 1.9 to 2.6, which itself introduced API changes that break old code. The Python version changed from 3.11 to 3.12. And the job launcher changed from direct python3 invocation to mpiexec through PALS, which sets different environment variables and has different rank-assignment semantics than NCCL's launcher.

These are not independent changes. They interact. The bf16 behavior on XPU interacts with the contrastive loss computation. The mpiexec launcher interacts with PL's DDP strategy detection. The PALS environment variables have different names than what torch.distributed expects by default. Porting is not a search-and-replace of 'cuda' with 'xpu' — it is a systematic audit of every point where the code assumes NVIDIA hardware, NVIDIA communication, or NVIDIA-era PyTorch behavior.

Two foundational contributions made this port possible. Addison Howe built a custom fork of PyTorch Lightning 2.6 with a full XPUAccelerator class — registering 'xpu' as a first-class accelerator, implementing XPU device detection via IPEX, and providing the biom3-env virtual environment on Aurora with all BioM3 dependencies at compatible versions. Without this, Lightning falls back to CPU and no GPU training is possible. Tarak Nandi developed the multi-node distributed training infrastructure — mpiexec launch scripts, PBS job templates for Aurora's capacity and production queues, GPU tile affinity via ZE_AFFINITY_MASK, and configuration systems for managing hyperparameters across pretraining and fine-tuning runs. Their combined work provided the platform on which the PenCL-specific fixes described in this note were built.

Why Aurora over Polaris

Polaris (ALCF)

4× NVIDIA A100 per node. CUDA + NCCL. The original PenCL was trained here. Known to work. 4-GPU DDP, 10 epochs ≈ 2 days on 4 nodes.

Aurora (ALCF)

12 tiles per node. At 4 nodes (48 tiles), each at 80% of A100 throughput, effective throughput ≈ 38× A100. 10 epochs ≈ 36 hours.

Aurora's advantage is density: 12 compute units per node versus 4. At equal node count, Aurora provides 3× more parallelism. For an experiment that requires multiple training runs (Run 1: corpus diversity alone; Run 2: corpus + sector loss), the difference between 2-day and 36-hour turnaround compounds.

Section 2 · The inference port

Six fixes to run the forward pass on XPU

In March 2026, we ported the full BioM3 pipeline (Stage 1 PenCL → Stage 2 Facilitator → Stage 3 ProteoScribe) for inference on a single XPU tile. This was the easier half of the port — inference is a forward pass with no gradient computation, no optimizer step, no distributed communication. Even so, it required six patches, each revealing a different assumption about the NVIDIA ecosystem baked into the codebase.

FIX 1 pynvml — NVIDIA monitoring crashes on XPU

pynvml is NVIDIA's GPU monitoring library. It calls into the NVIDIA driver at import time via nvmlInit(). On XPU, there is no NVIDIA driver — the import crashes with a NVMLError_LibraryNotFound. The library is used in three helper_funcs.py files (one per pipeline stage) for logging GPU memory usage during training and inference.

try: import pynvml pynvml.nvmlInit() HAS_PYNVML = True except Exception: HAS_PYNVML = False def print_gpu_initialization(): if not HAS_PYNVML: return 0.0 # ... existing pynvml monitoring code ...

The fix wraps the import in a try/except and guards every pynvml call with a boolean flag. This pattern is standard for optional hardware-specific imports, but pynvml was an unconditional import in three files — it had never needed to be optional because the code had only ever run on NVIDIA hardware.

FIX 2 Hardcoded accelerator — PL cannot find 'cuda'

PyTorch Lightning's Trainer was initialized with accelerator='cuda' in two files (Stage 1 and Stage 2 inference scripts). On XPU, this crashes because PL looks for CUDA devices and finds none. Addison Howe's custom Lightning build adds an XPUAccelerator class that registers itself under accelerator='auto'. Changing the hardcoded string to 'auto' lets PL's device-detection logic find XPU.

Pattern: never hardcode the accelerator string. Code that specifies 'cuda' explicitly is code that cannot run on any other hardware. 'auto' defers to PL's registry, which on Aurora finds XPU, on Polaris finds CUDA, and on CPU-only machines finds CPU. The same code runs everywhere.

FIX 3 Lightning 1.9 → 2.6 API change

The Polaris codebase used PL 1.9's instance method: model.load_from_checkpoint(path). PL 2.6 removed this — the correct call is the class method: type(model).load_from_checkpoint(path). This is not an XPU issue per se, but the Lightning version on Aurora (2.6, the ALCF custom build) is different from Polaris (1.9), so the port exposed it. Three files needed this change — one per pipeline stage.

FIX 4 strict=False — new keys in newer transformers

Aurora's environment has a newer version of the transformers library than Polaris. The newer version adds a position_ids buffer to BERT-family models that was not present when our checkpoint was saved. Loading the checkpoint with strict=True (the default) raises a RuntimeError for the unexpected key. Setting strict=False in load_from_checkpoint() ignores the mismatch. The new buffer is initialized correctly by the model — it doesn't carry learned parameters, so the missing key has no effect on model behavior.

FIX 5 Hardcoded 'cuda' in data preprocessing

preprocess.py — the dataset class that tokenizes proteins and text for PenCL — contained device = 'cuda' for placing tensors. On XPU, this fails silently or crashes depending on the operation. The fix replaces the hardcoded string with auto-detection:

if torch.xpu.is_available(): device = 'xpu' elif torch.cuda.is_available(): device = 'cuda' else: device = 'cpu'

FIX 6 XPU silent auto-cast to bf16

This was the most insidious fix. On NVIDIA hardware, tensors moved to the GPU with .to(device) stay in their original dtype (typically fp32). On Intel XPU, the Intel Extension for PyTorch (IPEX) can silently auto-cast inputs to bfloat16 for performance — a default behavior inherited from the inference-optimized IPEX configuration. The PenCL model expects fp32 inputs. When IPEX auto-casts to bf16, the model's fp32 weights and bf16 inputs produce a dtype mismatch in matrix multiplications, leading to silent incorrect results or explicit crashes depending on the operation.

# Before (works on CUDA): tensor = tensor.to(device) # After (works on both CUDA and XPU): tensor = tensor.to(device).float()

The .float() call is a no-op on CUDA (the tensor is already fp32) and a necessary correction on XPU (forcing the tensor back to fp32 after the device placement). This fix was applied in preprocess.py wherever input tensors are moved to the device.

Result: full pipeline on XPU

After these six fixes, the full BioM3 pipeline ran end-to-end on a single XPU tile: text prompt → PenCL embedding → Facilitator latent code → ProteoScribe sequence. The generated SH3 domain contained all hallmark motifs (ALYSYD, YEISFV, KWW, GICPSNYV, VSDIEG) with a Q-fraction of 0.032. Per-tile inference speed was ~39 iterations/second versus ~48 on an A100 — approximately 80% of NVIDIA throughput, consistent with published Ponte Vecchio benchmarks for transformer workloads.

Section 3 · Training-specific problems

Five additional fixes for the backward pass, loss computation, and training loop

Inference is a forward pass. Training adds the backward pass, the optimizer step, and — for contrastive learning — the synchronization of embeddings across GPUs so that the loss function can compare every protein against every text description in the global batch. Each of these introduced failures on XPU that did not appear during inference.

FIX 7 Distributed guards — 25 calls that crash on a single tile

PenCL's training code was written for multi-GPU DDP on NVIDIA hardware. Throughout the training step and validation step, the code calls dist.barrier() (synchronize all ranks before proceeding) and self.all_gather() (collect embeddings from all GPUs so the contrastive loss sees the full global batch). These calls require an initialized distributed process group. On a single XPU tile without DDP, dist.barrier() hangs indefinitely and self.all_gather() crashes.

The call count across the three PL wrapper classes: 13 dist.barrier() calls and 12 self.all_gather() calls. The primary class, pfam_PL_PEN_CL (selected by --dataset_type pfam), has 5 barriers and 4 all_gathers in training_step, 4 barriers and 4 all_gathers in validation_step. All three classes needed the fix — PL may reference parent or sibling class methods during training.

def _safe_barrier(): """Only call dist.barrier() if a process group exists.""" if dist.is_initialized(): dist.barrier() def _safe_all_gather(module, tensor, sync_grads=True): """In single-GPU mode, return the tensor unchanged. In DDP mode, collect from all ranks.""" if dist.is_initialized(): return module.all_gather(tensor, sync_grads=sync_grads) return tensor

These functions were added at the top of PL_wrapper.py, and every dist.barrier() was globally replaced with _safe_barrier(), every self.all_gather(x, sync_grads=True) with _safe_all_gather(self, x, sync_grads=True). In single-tile mode, the guards short-circuit and the code runs without distributed communication. In multi-tile mode with the XCCL process group initialized, they pass through to the real distributed primitives.

Why not just initialize a trivial 1-rank process group? This would work, but it adds unnecessary complexity and overhead (a process group has bookkeeping cost even with one rank). The guard pattern is cleaner: the code explicitly states "only synchronize if there are multiple ranks to synchronize with." It also makes the single-tile debug mode genuinely single-process, which simplifies profiling and debugging.

FIX 8 bf16 infinity masking — the contrastive loss diagonal

Contrastive learning computes a similarity matrix between all text embeddings and all protein embeddings in a batch. The diagonal entries — where each text is compared to its own paired protein — must be masked out so the model learns to match text to the correct protein, not to itself. The standard technique fills the diagonal with float('-inf'), which becomes −∞ after softmax, producing zero probability for self-matches.

On CUDA in fp32, float('-inf') is representable as the IEEE 754 negative infinity value. On XPU, the tensor may be in bfloat16 — either because of IPEX auto-casting or because mixed precision is enabled. bf16 has only 8 exponent bits and cannot represent infinity. The fill_diagonal_(float('-inf')) call in compute_inter_loss() in model.py raises a runtime error or produces NaN, depending on the operation sequence.

The fix casts the logits tensor to fp32 before applying the infinity mask. Alternatively, setting precision='32' in the Trainer eliminates bf16 entirely. We chose the latter for the initial port — correctness first, mixed-precision optimization later.

bf16 infinity is a recurring XPU pitfall. Any code that uses float('-inf') or float('inf') as sentinel values in masks, attention scores, or padding tokens is vulnerable. On CUDA, these sentinels work because fp32 is the default. On XPU with IPEX, the dtype may silently change. Audit every use of infinity in any codebase being ported.

FIX 9 Missing import — a side effect of Fix 1

The memory logging function print_memory_usage() in helper_funcs.py calls os.getpid(). On CUDA, pynvml was imported unconditionally at the top of the file, and pynvml imports os as a side effect. After Fix 1 wrapped pynvml in a try/except, the os import was no longer guaranteed. On XPU, with no NVIDIA driver, the try/except catches the pynvml failure and skips the import — including the transitive os import.

The failure mode was particularly frustrating: the training loop completed the forward pass, the backward pass, and the loss computation — then crashed on the print_memory_usage() logging call at the end of the training step, with a NameError: name 'os' is not defined. Adding import os at the top of helper_funcs.py fixed it.

Lost outputs. Two debug jobs ran with Fixes 7–8 but before Fix 9. Both crashed at the same point but wrote their logs to the same path, overwriting each other. We only diagnosed the issue after switching to unique log filenames with a timestamp suffix in the PBS script. Lesson: on shared job schedulers, always include $(date +%s) or a job ID in the log path.

FIX 10 Autocast disabled — PL does not know about XPU

PyTorch Lightning's mixed-precision plugin checks for CUDA to decide whether to enable torch.autocast. On XPU, the CUDA check fails and autocast is silently disabled, leaving the model in full fp32 regardless of the precision argument. The XPU-native autocast (torch.autocast(device_type="xpu", dtype=torch.bfloat16)) exists in PyTorch 2.10 and works correctly, but PL's precision plugin does not invoke it — the ALCF's custom Lightning build adds XPU accelerator support but does not extend the precision plugins.

For the initial port, we set precision='32' globally to eliminate the ambiguity. This means every operation runs in fp32 — slower than bf16 mixed precision, but numerically identical to the original CUDA training. Mixed-precision optimization is deferred to after the distributed training pipeline is validated.

FIX 11 Trainer configuration

The combined effect of Fixes 7–10 produces this Trainer configuration for single-tile XPU training:

trainer = pl.Trainer( max_epochs=args.epochs, devices=1, # one tile accelerator='auto', # custom PL auto-detects XPU strategy='auto', # no DDP for single tile precision='32', # fp32 everywhere — no autocast ambiguity num_nodes=1, callbacks=[checkpoint_callback, lr_monitor], logger=[tb_logger], log_every_n_steps=1, accumulate_grad_batches=args.acc_grad_batches, enable_progress_bar=True, enable_checkpointing=True, benchmark=False, # disable cuDNN benchmark (irrelevant on XPU) )

The complete fix catalog — 11 patches for CUDA → XPU. Fixes 1–6 solved inference. Fixes 7–11 solved single-tile training. Each fix addresses a distinct assumption about NVIDIA hardware or NVIDIA-era library behavior that was baked into the codebase. Together, they make the training loop device-agnostic: the same code runs on CUDA, XPU, and CPU without conditional branches in the training logic.

Section 5 · Distributed training on XPU

XCCL, mpiexec, and the decision to bypass Lightning's DDP launcher

On NVIDIA hardware, distributed training is straightforward: PL launches N processes via torch.distributed.launch, each process finds its GPU via LOCAL_RANK, and NCCL handles inter-GPU communication with near-zero configuration. On Aurora, nothing about this workflow transfers directly.

The XCCL backend

PyTorch 2.8 introduced native Intel GPU distributed support via the XCCL backend — a direct integration of Intel's oneAPI Collective Communications Library (oneCCL) into PyTorch's torch.distributed framework. This is distinct from the older external package oneccl_bindings_for_pytorch, which required a separate install and registered under backend='ccl'. The native backend uses backend='xccl' — using the old string 'ccl' will either fail or use a different code path. XCCL has been validated at scale on Aurora: 2,048 nodes (24,576 ranks) with 89% scaling efficiency for DDP workloads.

Why mpiexec, not Lightning's launcher

PL's built-in DDP strategy launches worker processes internally and manages rank assignment, device mapping, and environment variables. This works on NVIDIA because PL knows how to detect CUDA devices and assign them to ranks. On Aurora's custom Lightning build, the XPU accelerator is supported but the DDP launcher is not fully integrated with PALS (Aurora's job launcher) or the tile-level affinity masking needed for Ponte Vecchio's two-tile architecture.

The solution: bypass PL's process launcher entirely and use mpiexec directly. This approach follows the multi-node launch infrastructure developed by Addison Howe and Tarak Nandi for BioM3 Stage 3 pretraining on Aurora — their pretrain_multinode.sh scripts, PBS job templates, and GPU affinity patterns established the mpiexec-based workflow that we adapted for PenCL. The PBS job script launches 12 MPI ranks per node (one per tile). Each rank is an independent Python process that manually initializes torch.distributed with the XCCL backend before PL sees anything. PL then detects the already-initialized process group and wraps the model in DDP transparently — it doesn't need to know how the processes were launched.

GPU tile affinity: ZE_AFFINITY_MASK

Each MPI rank must be pinned to exactly one tile. Without pinning, all 12 ranks would see all 12 tiles and contend for the same memory. Intel's Level Zero runtime uses the ZE_AFFINITY_MASK environment variable to restrict which tile a process can access. With the mask set to a single tile index, torch.xpu.device_count() returns 1 from that rank's perspective.

#!/bin/bash # PALS_LOCAL_RANKID: 0–11 within a node # ZE_AFFINITY_MASK: which tile this rank sees export ZE_AFFINITY_MASK=$PALS_LOCAL_RANKID exec "$@"

The exec "$@" replaces the shell process with the Python command, keeping the environment variables intact. The PBS script invokes this via mpiexec --cpu-bind list:... /path/to/set_affinity_gpu.sh python3 PL_training.py ....

Manual distributed initialization

The distributed init code runs in PL_training.py after argument parsing but before any model or data creation. It reads rank information from PALS environment variables, exports the standard torch.distributed variables (RANK, LOCAL_RANK, WORLD_SIZE), and initializes the XCCL process group.

import os, torch, torch.distributed as dist if int(os.environ.get("WORLD_SIZE", 1)) > 1: world_size = int(os.environ["WORLD_SIZE"]) rank = int(os.environ["PALS_RANKID"]) local_rank = int(os.environ["PALS_LOCAL_RANKID"]) # Export standard vars that torch.distributed expects os.environ["RANK"] = str(rank) os.environ["LOCAL_RANK"] = str(local_rank) if not dist.is_initialized(): dist.init_process_group( backend="xccl", # native PyTorch 2.8+ init_method="env://", # reads MASTER_ADDR, MASTER_PORT world_size=world_size, rank=rank ) # With ZE_AFFINITY_MASK, each rank sees 1 tile → always xpu:0 torch.xpu.set_device(0) args.num_gpus = 1 # PL sees 1 device per process

Three discoveries during debugging deserve detailed explanation:

Discovery 1: PALS_LOCAL_SIZE, not PALS_WORLD_SIZE. The PALS environment provides PALS_LOCAL_SIZE (ranks per node) and PALS_LOCAL_RANKID (rank within node), but the variable name for the global world size is inconsistent across Aurora software versions. Our PBS script exports WORLD_SIZE explicitly to avoid ambiguity: export WORLD_SIZE=$((NNODES * 12)). The init code reads WORLD_SIZE, not PALS_WORLD_SIZE.

Discovery 2: the device is xpu:0, not xpu:local_rank. When ZE_AFFINITY_MASK isolates one tile per rank, each rank's torch.xpu.device_count() returns 1. The tile is always device 0 from the rank's perspective. Calling torch.xpu.set_device(local_rank) — which ranges from 0 to 11 — fails for ranks 1–11 because they only see one device. The affinity script handles the physical tile mapping; the Python code always addresses device 0.

Discovery 3: export WORLD_SIZE in the PBS script. torch.distributed.init_process_group with init_method="env://" reads MASTER_ADDR, MASTER_PORT, RANK, and WORLD_SIZE from environment variables. On NVIDIA systems, the launch utility sets these automatically. With mpiexec on Aurora, we must export them in the PBS script: export MASTER_ADDR=$(hostname) for single-node, export MASTER_ADDR=$(head -1 $PBS_NODEFILE) for multi-node. Without the explicit export, init_process_group hangs waiting for information that never arrives.

Trainer configuration for multi-tile

When launched via mpiexec, each process has already joined the XCCL process group and is pinned to one tile. The PL Trainer must use strategy='ddp' (not 'auto', which would try to auto-detect and potentially re-launch processes) with devices=1 and num_nodes=1 (mpiexec manages the multi-rank topology, not PL).

if dist.is_initialized(): trainer = pl.Trainer( devices=1, # mpiexec manages ranks accelerator='auto', strategy='ddp', # PL wraps model using existing process group precision='32', num_nodes=1, # mpiexec handles multi-node, not PL enable_progress_bar=(int(os.environ.get("RANK", 0)) == 0), ... ) else: trainer = pl.Trainer( devices=args.num_gpus, accelerator='auto', strategy='auto', # single-tile fallback precision='32', ... )

The enable_progress_bar guard ensures only rank 0 prints the progress bar — otherwise 12 processes compete for stdout and produce unreadable interleaved output.

Section 6 · Verification

Three tests, from 2 ranks to 12, and the memory wall

Distributed training was brought up incrementally — not by jumping straight to 12 ranks and hoping for the best, but by testing each component in isolation before combining them.

Test 1: XCCL 2-rank AllReduce

The minimal test: 2 MPI ranks, each creating a ones-vector on its tile, then AllReducing (summing) across both ranks. If both ranks see [2, 2, 2, 2], the XCCL backend, the affinity script, and the PALS environment variables all work correctly together.

# PBS: mpiexec -n 2 -ppn 2 set_affinity_gpu.sh python3 -c " import os, torch, torch.distributed as dist dist.init_process_group( backend='xccl', init_method='env://', world_size=int(os.environ['WORLD_SIZE']), rank=int(os.environ['PALS_RANKID']) ) torch.xpu.set_device(0) # affinity mask isolates 1 tile x = torch.ones(4, device='xpu:0') dist.all_reduce(x) print(f'Rank {os.environ["PALS_RANKID"]}: {x}') # Expected: both ranks print tensor([2., 2., 2., 2.]) dist.destroy_process_group() "

This passed on the first submission. The XCCL backend initialized without errors, the AllReduce produced the correct sum, and both ranks completed cleanly. This confirmed the fundamental communication pathway.

Test 2: 12-rank distributed init

Next: all 12 ranks on a single node forming the XCCL process group and initializing PL with the full training code. This test does not run training — it verifies that PL can detect the process group, wrap the model in DDP, and establish the Gloo peer connections used for CPU-side collectives (like checkpoint coordination).

This also passed. The log output showed all 12 ranks joining the XCCL process group, PL detecting strategy='ddp', and the Gloo backend establishing 12 × 11 peer connections for CPU-mediated operations. The model loaded on all 12 tiles. Then the job was killed.

Test 3: the OOM kill

Signal 9 — SIGKILL from the kernel's OOM killer. The 12-rank job died during data loading, not during training. Each of the 12 MPI ranks is a separate Python process, and each process independently loads the Pfam CSV (55 GB) via dask, the SwissProt CSV (5 GB), and the model weights (3 GB). The total memory consumption:

The 792 GB estimate is a lower bound — dask intermediate buffers, Python object overhead, memory fragmentation, and the OS itself push actual consumption past the 1 TB threshold. The OOM kill is deterministic: 12 copies of 55 GB will always exceed node memory.

The root cause is an interaction between our mpiexec architecture and PL's data loading design. In PL's built-in DDP, prepare_data() runs once on the main process, setup() runs per-GPU, and DistributedSampler ensures each GPU iterates a different slice of the data. With mpiexec, there is no "main process" — all 12 ranks are independent Python processes that each call prepare_data() and setup() independently. The code's prepare_data() uses self.trainer.world_size to decide how many splits to create — but PL sees world_size=1 (it thinks each process has one device), so it creates no splits, and each rank loads the entire CSV.

The fix: rank-aware data splitting

The fix modifies prepare_data() to read the real world size from torch.distributed instead of PL's Trainer, and to coordinate via a barrier so that rank 0 creates the splits and all other ranks wait for them.

def prepare_data(self): if dist.is_initialized(): world_size = dist.get_world_size() rank = dist.get_rank() else: world_size = 1 rank = 0 if rank == 0: # Rank 0 splits 44.8M Pfam rows into N shards pfam_df = dd.read_csv(self.pfam_path, ...).compute() for shard_idx in range(world_size): shard = pfam_df.iloc[shard_idx::world_size] shard.to_csv(f"split_pfam_rank_{shard_idx}.csv", index=False) print(f"Split Pfam into {world_size} shards") if dist.is_initialized(): dist.barrier() # all ranks wait for rank 0 def setup(self, stage=None): rank = dist.get_rank() if dist.is_initialized() else 0 self.pfam_df = pd.read_csv(f"split_pfam_rank_{rank}.csv")

After splitting, each rank loads ~4.6 GB instead of 55 GB. The total memory budget drops from 792 GB to approximately 187 GB — well within the 1 TB node capacity.

This fix is a prerequisite for multi-node, not an optimization. At 48 ranks across 4 nodes, 48 × 55 GB = 2.6 TB — far beyond the 4 TB total across all nodes. Every rank must load only its shard. The same prepare_data() fix scales unchanged from 12 to 48 ranks — rank 0 creates 48 shards, the barrier synchronizes, and each rank loads its own shard.

Section 7 · The PBS scripts

Everything that must be set before Python runs

The PBS script is where all the Aurora-specific complexity lives — the module loads, the affinity masking, the environment variable exports, the mpiexec invocation. The Python code is (mostly) device-agnostic after the fixes. The PBS script is where the device-specificity concentrates.

Several elements deserve explanation. -j oe joins stdout and stderr into one file — critical for debugging because error messages from rank 5 and print statements from rank 0 end up in the same log. unset CCL_PROCESS_LAUNCHER clears a stale variable set by the frameworks module that can interfere with XCCL initialization. The CPU_BIND list pins the 12 MPI ranks to specific physical cores distributed across both sockets, avoiding core contention.

For multi-node, the script changes minimally: #PBS -l select=4, MASTER_ADDR=$(head -1 $PBS_NODEFILE), and mpiexec -n 48 -ppn 12. The Python code is identical.

The 2 seconds per step estimate is based on A100 throughput scaled to 80% for XPU after JIT warmup. The actual per-step time at 48 tiles depends on gradient synchronization overhead — the AllReduce for 107M trainable parameters across 48 ranks via Slingshot-11. At 89% scaling efficiency (the XCCL benchmark on Aurora), the effective time is ~2.2 seconds per step, giving ~4.0 hours per epoch.

Why 10 epochs? We do not know a priori how many epochs are needed. The original PenCL used 5 epochs for the design application and 20 for benchmarking. Our corpus is 9× larger per protein (9 text variants) but also 9× more diverse. We start with 10, checkpoint every epoch, and evaluate embedding geometry at epochs 2, 5, and 10. If format invariance plateaus before epoch 10, we stop early. If it hasn't converged by epoch 10, we extend.
